SamOS Principles

The SamOS Principles are the rules the system uses to make decisions. They keep SamOS practical, flexible, and focused on solving real problems without creating unnecessary complexity.

  1. Optimize for Present Sam.

    Design around my actual brain, environment, and constraints based on my patterns and behaviors. I do not have to change for systems that do not work for me. I can change those systems instead.

  2. Build for Future Sam.

    Make choices that reduce friction for the version of Sam that has to deal with it later (Future Sam). Present Sam should leave things easier, clearer, or more usable.

  3. Progress over perfection.

    A useful imperfect system is better than a perfect system that never gets finished. Keep moving.

  4. Document reality, not ideals.

    Document how things actually work, not how you wish they worked.

  5. Let patterns emerge.

    Don’t force structure. Use the system first, then organize around the patterns that actually appear.

  6. Design for interruption and easy resumption.

    Assume I will get interrupted. Make it obvious where to pick back up without having to rebuild everything.

  7. Work backwards from the problem.

    Start with the thing that needs to be solved, then build only what helps solve it.

  8. Solve today’s problems before tomorrow’s.

    Don’t overbuild for hypothetical future needs. Fix the real problems that I'm having right now.

  9. Every process must earn its place.

    A process should exist because it provides clear value. If it only adds steps, it probably does not belong. If it doesn't belong, get rid of it.

  10. When in doubt, remove a layer.

    Processes shouldn't be copmlex just for the sake of it. If something feels too complicated, simplify before adding more.

  11. Measure useful assets, not activity.

    Track what I created or improved, not how busy I looked while doing it.

  12. Preserve history.

    Capture meaningful changes, decisions, and outcomes. Avoid documentation that exists only for the sake of documentation.

  13. Do not maintain competing sources of truth.

    Important information should have one clear home. Duplicate versions create confusion and extra maintenance.

  14. Prefer simple words over clever words.

    Clear language is more useful than impressive language. Make things easy to understand.

  15. Start boring; add complexity only when it solves a real problem.

    Begin with the simplest version that works. Add features, structure, or automation only when they have a reason to exist.
